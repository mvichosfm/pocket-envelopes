# CLAUDE.md — pocket-envelopes

Orientation for Claude Code sessions opened anywhere under this folder.

## What this is

A single-file personal-finance web app focused on envelope budgeting, built by and for a two-earner household; the author's own budget is the primary test bed. MIT-licensed.

## Architecture invariants — don't break these

- **Single file**: `pocket-envelopes.app` stays one file. No bundler, no modules, no `<script src>` to local JS, no build step. Do not refactor into per-tab modules.
- **No runtime npm deps**. The one external script is Chart.js, **vendored locally** at `vendor/chart.umd.min.js` (loaded line ~7). Don't add CDN scripts.
- **stdlib-only Python**. `serve.py` must not require `pip install`. If you find yourself wanting a Python lib, put it in a sibling helper that's clearly optional.
- **Local-only**. The app talks to `127.0.0.1` only. No outbound network calls. No telemetry. No auth.
- **Server-backed persistence for `finance-data.json`** (since the `server-persistence` branch). The app `GET /data` on load and `PUT /data` on save — debounced 1.2s after edits, and immediately on `blur` / `visibilitychange:hidden` / `pagehide` via `flushNow()` (which uses a `keepalive` fetch, capped at 60KB by spec). Any browser works; there is no File System Access permission and no IndexedDB handle. `serve.py` owns the file: atomic write (`.tmp` + `fsync` + `os.replace`), rolling `finance-data.bak.0…4`, `400` on invalid JSON, and ETag/`If-Match` optimistic concurrency with a `409` conflict dialog. See decision #29.

## Data model

```
data = {
  version: 2,                  // schema version, see migrate()
  accounts: [{ id, name, type, openingBalance, includeInNetWorth, isInvestment?, pinned?, owner?, archived? }],
  envelopes: [{ id, name, budgetAmount, cadence: 'monthly'|'annual', rolloverPolicy: 'rollover'|'reset'|'sweep', category?, pinned?, isReserve?, accountId?, archived? }],
  // archived?: true hides the record from lists, pickers, Fund the month, close-out and the forecast's
  // default selection; history and balances are untouched. An archived envelope has no budget
  // (envMonthlyEquiv → 0). The field is deleted, not set false, on unarchive.
  // accountId?: the account that holds this envelope's money ("Backed by"). undefined = household-wide.
  // A filtered forecast subtracts only household envelopes plus those backed by a selected account,
  // and drains a backed envelope's allowance from that account. Always absent on the reserve envelope.
  // isReserve: the single emergency / catch-all envelope. budgetAmount is forced to 0,
  // it is never listed in "Fund the month", and it is the destination of close-out sweeps.
  transactions: [{ id, date: 'YYYY-MM-DD', type, amount, accountId?, envelopeId?, fromAccountId?, toAccountId?, fromEnvelopeId?, toEnvelopeId?, payee, notes, fromRecurringId?, splits?, source?, tag? }],
  // splits?: [{envelopeId, amount}] on an expense/income tx — the account is debited by `amount`,
  // which is allocated across envelopes (splits sum === amount; envelopeId is null when split). source?: 'import'.
  // tag?: the NAME of an entry in settings.tags (a string, any tx type incl. transfers); undefined = untagged.
  recurring: [{ id, name, type, amount, schedule: 'weekly'|'monthly'|'custom-months', startDate, months?[], accountId?, envelopeId?, ..., active, lastAppliedDate, tag?, skippedDates? }],
  // rec.tag is copied onto every transaction recurringToTx() generates.
  // skippedDates?: ISO dates the user chose to Skip in the due review — always AFTER lastAppliedDate
  // (pruned once the watermark passes them). Both pending-occurrence readers honour it via isSkippedOccurrence().
  // Note: `dayOfMonth` appears in demoData() but nothing reads it — occurrences anchor on startDate.
  snapshots: [{ date, value }],     // net worth, one per day
  forecastProfiles: [...],
  importProfiles: [{ id, name, delimiter, hasHeader, dateOrder, amountMode, map:{date,desc,amount,debit,credit}, accountId }],  // saved CSV-import column mappings
  defaultForecastProfileId,
  settings: { currency, locale, theme: 'auto'|'dark'|'light', household: ['You','Partner'], tags: ['Fixed costs', ...], tagLimit?, forecastWarnBelow? }
  // forecastWarnBelow?: number — the dashboard's low-point tile turns amber under this amount (red below zero regardless). Absent = no floor.
  // tags: ordered list of tag names, at most tagLimit() in the UI; order = chip/chart colour index (repeats after 8).
  // tagLimit?: integer 1–50 (Settings → Tag limit); absent = TAG_LIMIT_DEFAULT (8). migrate() drops any other value.
  // Lowering it never truncates the list — it only disables "+ Add tag".
}
```

**Transaction types**:
- `expense`: account ↓, envelope ↓ (consumed)
- `income`: account ↑, envelope ↑ (funded)
- `transfer-account`: from-account ↓, to-account ↑, no envelope effect
- `transfer-envelope`: from-envelope ↓, to-envelope ↑, no account effect

**Recurring `lastAppliedDate` semantics**: occurrences ON or BEFORE this date are considered already-applied (a real `transactions[]` entry exists). Anything after is unapplied / future. Past-but-unapplied = "due", surfaced via `dueRecurringOccurrences()`.

## Recent decisions worth preserving

1. **Delete refuses orphans, not cascades.** `deleteAccount` / `deleteEnvelope` block the delete with an `alert()` listing the linked-record count. Reasoning: silent orphans break net worth; cascade deletes destroy history irretrievably. User must clear refs first.
2. **Forecast folds due recurrings into idx 0.** Without this, "lowest in period" is optimistic by exactly the sum of unapplied dues. The fix is in `forecastAccountBalances` right after the envelope-total seed. Don't move it after the future-projection loop — it must contribute to idx 0 specifically.
3. **Refill modal binds by envelope.id, not array index.** Two-tab race protection. Same pattern should apply to any future modal that mutates a `data.*[]` list selectively.
4. **Light-theme semantic tokens are darker.** `[data-theme="light"]` overrides `--accent`, `--accent-2`, `--warn`, `--bad`, `--good`, `--chart-grid`, `--chart-total`. Dark-mode hues (`#56d364`, `#e06c75`, `#f0a64a`) fail WCAG AA on white; the overrides (`#1a7f37`, `#cf222e`, `#9a6700`) pass. Don't add hardcoded chart colours — route everything through `themeColor()` / `chartPalette()`. The same goes for text sitting **on** a solid semantic fill (primary/danger buttons, the done-step marker, the import "dup?" badge): use `--on-fill` (dark ink in the dark theme, white in light), never a literal — a literal dark ink was invisible on the light theme's darker accent until 2026-09-07. **Surfaces retuned 2026-09-08:** the light theme is now white sheets (`--bg-2: #ffffff`) on a cool light-grey desk (`--bg: #eceef2`) with a card-only shadow token (`--shadow-card`, defined in light only; `.card` reads it with a `none` fallback so dark stays flat) and a distinct inset tone (`--bg-3`) for inputs, buttons and tiles. The manila-on-manila version had no card separation and its secondary buttons vanished. Ghost buttons carry a transparent 1px border everywhere so a hover border can appear in light without shifting layout.
5. **Mini calculator in Amount fields.** `type="number"` strips operators, so Add Tx and Move Funds use `type="text" inputmode="decimal"` + `evalAmount()` on save. Don't revert to `type="number"`.
6. **Account balances appear next to names** in the tx-modal account dropdowns — three places (`t_acc`, `t_facc`, `t_tacc`). If you add a new account select anywhere, follow the pattern (`${esc(a.name)} — ${fmt(accountBalance(a))}`).
7. **License is MIT.** Don't change without asking.
8. **Undo is snapshot-based, not command/inverse-op.** `pushUndo(label)` deep-clones `data` BEFORE each destructive mutation; `performUndo()` pops and restores. Ring-buffered to 30 (RAM cost ~MB-scale at realistic data sizes). In-memory only; reloads clear the stack. Don't switch to per-action inverse ops — generic + cheap + correct beats clever, and it covers batch ops like ⚡ apply-due-recurring for free. Wired to Ctrl-Z and to the Undo button inside the toast after every delete.
9. **Sync flush on tab teardown.** The 1.2s debounce in `saveDirty()` would strand the last edit if the user closed the tab / backgrounded the mobile app mid-debounce. `flushNow()` cancels the timer and fires the save immediately. Since the server-persistence change this is a `fetch(..., {keepalive: true})` PUT rather than a synchronous localStorage write; keepalive is spec-capped at 64KB, so `writeFile` only sets it under 60KB and a larger file falls back to an ordinary fetch (see decision #29 for why that residual risk is small).
10. **Rolling backups live in `localStorage`, not on disk.** File System Access only gives the app a *file* handle, not the parent directory, so writing sibling `.bak` files would require switching to `showDirectoryPicker()` (significant UX change). Backups are stored as one `envBudget_bak_<date>` key per day with a small `envBudget_bak_index` for the slot list. Trade-off: clearing site data wipes backups. Disk-level backups via directory picker remain on the roadmap. Restore goes through `pushUndo()` so a wrong restore is Ctrl-Z-able.
11. **Add/Edit transaction snapshots undo.** The `t_save` handler (Add Tx / Edit Tx / recurring-instance-now) calls `pushUndo('Add transaction' | 'Edit transaction')` *before* the push/overwrite. This is the highest-frequency mutation and was previously the one destructive site that did NOT snapshot — so Ctrl-Z popped an older snapshot and reverted an unrelated earlier change while the just-edited tx survived. Reinforces #8; don't remove it. (Fixed 2026-05-31, review-360.)
12. **Due-review "Apply selected" advances `lastAppliedDate` only through the contiguous applied prefix.** In `showDueReview()`'s `dueApplySel` handler, each recurring's watermark may advance only up to its latest applied occurrence that has **no earlier un-ticked sibling** — NOT to the max applied date. 22. **Envelopes have a projected balance series, floored at zero — this is what makes "Lowest spendable in period" correct (2026-08-01).** `spendable = total − envelopeTotal`, so an envelope balance is money the spendable line has *already* set aside. The old code drained the allowance from the account but deliberately left `envelopeTotal` frozen (the removed comment argued that mirroring it would push envelopes to −∞). That charged every funded euro **twice** — once as a reservation, once as the account outflow that spends it — so "lowest spendable" was understated by exactly the funded balance (synthetic example: 1000 cash, 300 funded, 300-a-month budget projected a 60-day low of **99** instead of **400**). Because `refillEnvelopes()` uses that number as "max safe to fund today" and soft-blocks on it, **funding an envelope made the app say funding was unsafe** — in the same example, topping the 300 envelope up to 600 warned "over-allocates by 201". Fix: `forecastAccountBalances` keeps `envSeries[envId]` per envelope, mirrors the allowance drain onto the owning envelope, and aggregates with `if (s[i] > 0)` — "spend the envelope down, *then* eat unallocated cash". The floor is what makes the mirror safe, and it fixes the opposite error too: a recurring draining an envelope monthly used to walk `envelopeTotal` to −∞, pinning spendable flat and pretending the bill was free. **Don't revert to a single running `envelopeTotal`, and don't remove the floor** — they're one mechanism, not two changes. Note the floor also applies at idx 0, so an *already*-overspent envelope now correctly reduces today's spendable instead of inflating it.
23. **Recurring coverage of an envelope allowance is an amount, not a flag (2026-08-01).** `envelopeIsCoveredByRecurring` (boolean) is gone; `recurringMonthlyForEnvelope(env)` returns how much of the budget active recurrings already model, and the allowance projects `budget − covered`. 27. **The Fund modal re-forecasts; it does not do `spendMin − total` (2026-08-01, same day as #22 — this was the missing half of it).** Funding used to be projected arithmetically, assuming each funded euro lowers the spendable line by a euro on every day. 28. **"Fund the month" assigns the budgeted amount; it does not top up to the budget (2026-08-01).** `envelopeFundSuggestion(env,'month')` returned `max(0, budget − bal)` for monthly envelopes — which is *identical* to `'full'` mode, so the two dropdown options only differed for annual envelopes, and "Fund one month" silently repaid overdrafts. On a real 12-envelope month the proposal exceeded one month's budget by exactly the sum of the overspends — repair the user never asked for (synthetic example: a 1000-a-month envelope sitting at −735 was funded 1735 to land at exactly 1000). Now `'month'` funds `budgetAmount` for monthly and `budgetAmount/12` for annual, ignoring the current balance — so in that example the envelope funds 1000 and **lands at 265**, and last month's overspend is felt this month, which is the point of envelope budgeting. `'full'` is unchanged and is now the meaningfully different option ("bring the balance up to target"). **Only annual keeps the headroom cap**, and the asymmetry is deliberate: for an annual envelope `budgetAmount` is a *target balance* (the amount to have saved by year end) so accruing past it is meaningless, while for a monthly envelope it is a *monthly flow* with no ceiling — a rollover envelope accumulating is exactly what rollover is for. Knock-on: because an overspent envelope now lands lower, less of the funding survives to the forecast's low point, so the projected-spendable warning improves too (measurably higher at the low point in the reproduced case). 29. **The server is the single source of truth; the browser holds no authoritative copy (2026-08-15, `server-persistence` branch).** The File System Access path is gone — handle-in-IndexedDB, `queryPermission`/`requestPermission`, the click-to-reconnect indicator, `openFile`, and the "Allow on every visit" tip all deleted. `serve.py` now owns `finance-data.json`: `GET /data` (ETag = sha256, `X-Data-New: 1` when the file doesn't exist yet) and `PUT /data` (validate → rotate `.bak.0…4` → `.tmp` + `fsync` + `os.replace`). It binds loopback by default (`BIND=0.0.0.0` is the opt-in for tailnet peers), and **there is no authentication** — reachability is the whole access-control story, which is why the README says to keep the port off the LAN. Three consequences worth holding on to: (a) **the localStorage data mirror (`LS_KEY`) was removed, not just bypassed.** With several devices on one file, a per-browser mirror is as likely to be a stale copy of someone else's older state as it is to be a lost edit, so hydrating from it would resurrect deleted transactions. Recovery is now the server's `.bak.N` rotation plus the *dated* localStorage backups (Settings → Backups), both of which the user picks deliberately. The daily-backup slots stay — they're the only local-history layer left. (b) **A failed save must not silently look like a success:** `writeFile` returns a boolean and every caller checks it, because "saved" now depends on a network hop that can fail. (c) **`demoMode` is what protects the real file from `?demo=1`** — the old code relied on `fileHandle` being null, and there is no handle any more; `writeFile` returns before the fetch. Verified: a demo session makes no `/data` request at all.

30. **Concurrent edits are refused, never merged (2026-08-15).** Every `GET`/`PUT` hands back an ETag; `writeFile` sends it as `If-Match`, and a mismatch comes back `409` with the server's current tag. `handleConflict` pauses auto-save and offers reload / force-overwrite / keep-working — it never touches `data`, so the tab's unsaved work survives whichever choice the user makes. A forced overwrite still rotates the version it replaces into `.bak.0`, so "my version wins" is recoverable. Omitting `If-Match` is *accepted* by the server on purpose (single-user app, and Import genuinely means "this file wins"); don't make it draconian, and don't add a last-write-wins auto-retry — the visible conflict is the feature.

31. **Installable PWA: cache the shell, never the data — and "unreachable" usually means 502, not a thrown fetch (2026-08-15).** The app is served over a real HTTPS origin by `tailscale serve` (`https://<host>.<tailnet>.ts.net` → `127.0.0.1:8765`), which is what makes it installable at all; a secure context is a hard requirement for manifests and service workers. Three decisions inside `sw.js` that are easy to "simplify" and must not be: (a) **`/data` is never cached or even intercepted** — the fetch handler returns early for it. A cached budget renders stale figures that look authoritative, and offline writes would replay as a wall of 409s against a stale ETag; the conflict dialog is built for "two devices occasionally", not a day of queued edits. Offline *editing* needs a merge layer and is a separate project. (b) **The shell is network-first, not cache-first** — cache-first would resurrect the stale-app-code bug the no-store headers were added to kill, and against a LAN server the network hop costs a millisecond. (c) **A non-ok response falls back to cache, not just a thrown fetch.** This was a real bug caught in testing: with `tailscale serve` in front, stopping `serve.py` yields **HTTP 502**, which `fetch()` resolves rather than throws — so the original throw-only fallback never fired and Chrome's error page won. Since the proxy staying up while the backend sleeps is the *common* failure here, the `!fresh.ok` branch is the one that actually earns the service worker its keep. Verified by stopping the server and reloading: app boots from cache and shows its own "server error 502" state. Bump `CACHE_NAME` to force clients onto a new shell.

32. **The always-on server is a boot task running as SYSTEM, and its launcher must block (2026-08-15).** `PocketEnvelopesServer` triggers `AtStartup` rather than at logon, so the app is reachable from a phone after a reboot with nobody signed in. That forces the account choice: a boot-time task cannot run as an interactive user without storing that user's password, so it runs as `SYSTEM` (`LogonType ServiceAccount`, no credentials). Registration therefore needs elevation — a non-elevated `Register-ScheduledTask` fails with "Access is denied". Two consequences that were verified, not assumed: (a) `SYSTEM` finds Python because it is a machine-wide install on the *machine* PATH — a per-user Python would break the task while working fine when run by hand, so check `[Environment]::GetEnvironmentVariable('Path','Machine')` before blaming anything else; (b) `finance-data.json` ends up **owned by SYSTEM**, which is harmless because the ACLs are inherited from the folder and the interactive user's account keeps FullControl — confirmed by reading and touching the file after a SYSTEM-issued write. **`serve-daemon.cmd` runs Python in the foreground, not via `start /b`** — the script *is* the task's process, so blocking is what makes the task track the server: State shows `Running` while it serves, stopping the task really stops it, and a crash ends the task with an error so the restart policy fires. Detaching made the task report success one second after boot and left the server unsupervised. Don't "fix" that back into a `start /b`.

33. **The reserve envelope is a flag, not a new concept — and sweeps are envelope-to-envelope transfers (2026-08-18).** An emergency / catch-all envelope is just an envelope carrying `isReserve: true`. Everything that makes it behave differently falls out of two facts rather than a parallel code path: (a) **`budgetAmount` is forced to 0** on save, which is what keeps it out of the forecast's allowance projection (`envMonthlyEquiv` → 0 → the `budgeted <= 0` `continue` in `forecastAccountBalances`), out of the monthly-budget totals, and out of "how much of the budget is unfunded" arithmetic — no new guards anywhere; and (b) the Fund modal iterates a `fundable` list that filters reserves out, because a reserve holds money that was already budgeted once (swept out of other envelopes), so proposing to fund it again would double-allocate it. `rolloverPolicy` gains a third value `'sweep'`, and close-out gains a matching action that posts a **`transfer-envelope`** — positive leftover → reserve, and an *overspent* envelope is brought back to zero *out of* the reserve, which is precisely what an emergency buffer is for. Transfer, not the one-sided expense/income that `reset` uses, is the whole point: the money stays earmarked, so spendable cash is unchanged on a positive sweep (verified: spendable identical before and after with only positive leftovers). Note the asymmetry that decision #22's zero floor creates and which the help text now states explicitly: covering an overspend from the reserve **raises** spendable, because a negative envelope was already floored out of `envelopeTotal` and reserved money has now filled the hole (verified: spendable rose by exactly the overspend that was covered). **At most one reserve** — `editEnvelope` clears the flag from every other envelope on save, because the flag *is* the sweep destination and two would make "sweep to the reserve" ambiguous; `reserveEnvelope()` still takes the first defensively so a hand-edited file can't break close-out. A `'sweep'` policy saved while no reserve exists degrades to `'rollover'` rather than silently behaving like one. Getting money back out is the pre-existing **Move funds** (`transferEnvelopes`) — no new UI was needed for the half of the feature that already worked.

34. **The current month drains what is LEFT of each envelope's budget, not a fresh full month (2026-08-19).** Decision #24's `catchUpFactor` redistributed the *elapsed* part of the month into the days remaining, so on the 19th of a 31-day month the whole monthly allowance drained across the last 12 days — on top of the spending that had actually happened in those 19 days and was already inside `accountBalance()`. The month was charged twice. Measured on real data (12 envelopes): the projection was **low by one constant at every horizon — 30, 90 and 365 days** — and that constant was, to the cent, the month's posted envelope spending; it also manufactured a spendable dip 8 days out that did not exist (the true line was flat). The constant offset across all horizons is the fingerprint: a one-off current-month over-charge, not a rate error. Now `spentThisMonth[envId]` is computed once per forecast (split-aware via `txEnvelopePortion`, one-sided bookkeeping excluded via `isCashflowTx`, and occurrences of a recurring that already *covers* the envelope skipped so decision #23's netting isn't applied twice), and the current month drains `max(0, monthly − spent)` over `remainingAfterToday`. **Decision #24's invariant is intact and re-verified**: every *future* calendar month still drains exactly one month's allowance (measured: the same one-month total for each of the 12 following months; the partial head and tail months pro-rate correctly). What moved is only the current month's rate, which now tracks real spending — the stability #24 wanted applies to a minimum falling in a future month, which is the usual case. The zero floor matters here too: an envelope already spent past its budget projects **no** further allowance rather than a negative drain that would silently credit the account back (verified — a probe spend larger than an envelope's monthly budget removed precisely that envelope's remaining allowance and nothing more). `catchUpFactor` is gone; `allowanceInfo.calendarAnchor` keeps `todayDay`/`remainingAfterToday` as console diagnostics only.

35. **The close-out review is a wide, single-scroller dialog, and its table restacks rather than scrolling sideways (2026-09-01).** Six columns in the 520px default modal forced a horizontal scrollbar — which for a figures table is the one scroll direction that hides data, since the Action select (the only control in the dialog) sat off-screen. 36. **Transaction tags are a name string on the record, referencing a small ordered list in `settings.tags` — and they apply to transfers too (2026-09-06).** One optional `tag` per transaction and per recurring template; `TAG_LIMIT = 8` is a UI cap, not a schema rule. Six things worth holding on to: (a) **Tags answer a different question than envelopes.** Envelopes say what the money was for; the tag axis is how committed the money is (Income · Debt & taxes · Fixed costs · Essentials · Lifestyle · Occasions · Work · Savings in the author's file) — which is also what makes the envelope-less flows (loans, taxes, subscriptions, insurance) reportable for the first time. Don't turn tags into a second category tree. (b) **Transfers can carry a tag, and a tagged transfer counts as outflow in the tag reports** — `reportsAggregates` counts `expense && isCashflowTx` plus `transfer-account && tx.tag`. The reason is the "petty cash" pattern: work-reimbursable outlay, savings contributions and loan repayments are all modelled as transfers, and they are precisely what `Work`, `Savings` and `Debt & taxes` exist for. An untagged transfer stays internal movement. Only the outgoing leg of a pass-through loop should be tagged, never the reimbursement coming back, or the report double-counts. (c) **Stray tags are kept, not dropped.** `migrate` sanitises the list (trim, case-insensitive dedupe) and snaps a record's tag to the canonical spelling, but a tag naming nothing in the list survives: `migrate` runs before any `pushUndo`, so dropping it would be silent, irreversible data loss on an import from a device whose list was edited later. Stray tags render as a grey chip, show up in `allTags()` (filters, report columns) and the edit form lists them as "(unlisted)" so save can't clear them by accident. (d) **The tx save handler rebuilds `out` from literals**, so `tag` is copied across explicitly — same trap the `fromRecurringId` comment documents; the recurring save spreads `...r` and therefore has the *opposite* problem (a cleared select would keep the stale value), hence the explicit `tag: value || undefined`. (e) **Colour = list index into `chartPalette()`**, the last palette entry being reserved for "Untagged" in the doughnut; chip and slice share `tagColor()`, and the chip gets it as an inline `--tag-c` custom property so no hex lives in JS. Deleting a tag shifts later colours — accepted, both renderers shift together. (f) **The Reports doughnuts now go through `reportCharts[]`**, destroyed in `render()` next to `currentChart`. Before this the envelope doughnut was created bare and never destroyed — `innerHTML` removed its canvas but Chart.js kept the instance and its resize observer, one leak per Reports visit (verified: `Chart.instances` now stays flat across repeated visits). `suggestPayeeDefaults` learned to return `tag` (from every tx type with that payee, whereas account/envelope still come from expense/income only), so after a backfill new entries auto-tag from history; the payee-blur handler was restructured so the tag suggestion fires for transfers too.

37. **The Windows installer is per-user, bundles its own Python, and keeps the budget out of the program folder (2026-09-06).** Four choices, each with a reason: (a) **per-user install, no elevation** — `PrivilegesRequired=lowest` puts the program under `%LOCALAPPDATA%\Programs`, so there is no UAC prompt and nothing under Program Files, which is read-only for the very process that needs to write the budget; (b) **`DATA_DIR`** — `serve.py` now resolves the data file, temp file and backup rotation under `os.environ["DATA_DIR"]` when set (static files still come from the script's own folder), and `launcher.py` sets it to `%LOCALAPPDATA%\PocketEnvelopes` so the budget survives uninstall and reinstall; the uninstaller says so in a message rather than deleting it; (c) **the launcher runs the server in-process** under the bundled `pythonw.exe` rather than spawning a detached child: a second launch detects the open port and only opens the browser, the browser is opened by a thread that waits for the port to accept, and since `pythonw` has no console `sys.stdout`/`sys.stderr` are redirected to `server.log` — without that, `BaseHTTPRequestHandler.log_message` would throw on every request; (d) **upgrade and uninstall stop a running server first** through a `[Code]` hook that kills only Python processes whose command line contains this install's `launcher.py`, so other Python on the machine is untouched. Verified end to end with silent install → launch on a test port with the bundled runtime → `GET /` / `GET /data` / `PUT /data` / static data file refused → upgrade over a running server → uninstall over a running server → data folder intact and no leftover process. The installer is unsigned; SmartScreen warns, and the release page prints the SHA-256.

38. **A skipped recurring occurrence is a date on the template, not a moved watermark (2026-09-08).** Decision #12 said a permanent skip must be a deliberate action; until now there was none, so an unticked due occurrence came back in every review. The due review now offers Record / Skip / Decide later per row. A skip appends the date to `rec.skippedDates`; `firstPendingOccurrence`, `dueRecurringOccurrences` and the dashboard's Upcoming panel filter through `isSkippedOccurrence()`. `lastAppliedDate` keeps its one meaning and still only advances through the **contiguous resolved prefix** (recorded *or* skipped, up to the first "decide later"); afterwards skips at or before the watermark are pruned, so the list holds at most the few dates between the watermark and today. Verified: skipping the only due occurrence advances the watermark and leaves no list; skipping a later occurrence across a "later" gap keeps it in the list, still hidden from due, until the earlier one is recorded. The forecast is untouched — it projects from tomorrow and skips are past dates. The review itself is one `pushUndo` (it was the one batch mutation that had none), and its amount fields go through `evalAmount()` like every other amount. The Recurring tab's ⏭ button (`skipRecurringOccurrence`) is the single-row form: the first pending occurrence is by definition the earliest unresolved one, so skipping it just advances the watermark to that date — no list entry needed — and it works on a future occurrence too, which removes that bill from the forecast.

39. **The Transactions tab keeps its filter across renders, and every account/envelope name is a drill-through into it (2026-09-08).** `txFilter` is module-level state read by `renderTransactions` and written by the filter controls; `render()` never resets it, so editing one row no longer clears the filters, and `goToTransactions({acc|env})` plus `?acc=&env=&tag=&q=&from=&to=` URL params are the same mechanism pre-filled. The filter pass, the initial render and the dashboard's Recent list all sort through one `sortTxsDesc` (date desc, then insertion order) — the filter used to sort by date alone, so same-day rows reshuffled on the first keystroke. The caption totals **cash** only (`isCashflowTx`): transfers and one-sided envelope bookkeeping are excluded, and the tooltip says so. Bulk edit (tag / envelope / delete over ticked rows) is one snapshot per operation; the envelope change skips transfers and split transactions and reports the count rather than touching them. Redo (`performRedo`, Ctrl+Y / Ctrl+Shift+Z) is the same snapshot mechanism mirrored; `pushUndo` clears the redo stack, the usual linear-history rule.

40. **Scheduled transactions are labelled, not counted (2026-09-08).** `accountBalance` / `envelopeBalance` have always stopped at today; the lists now badge anything dated after today as "scheduled" (`txDateCell`, shared by both tables) and the Accounts tab prints the net scheduled amount under each balance. No accounting change — the alternative, counting future rows into balances, would silently make "what my bank shows" wrong.

41. **An envelope can name the account that holds its money, and a filtered forecast subtracts only the envelopes its accounts hold (2026-09-08; closes roadmap #20).** `spendable = total − envelopeTotal` mixed a *filtered* account set with an *unfiltered* envelope set, so a per-person forecast profile charged the other partner's envelopes against this partner's cash (a 500 account with 300 of envelopes funded elsewhere reported spendable 200), and the Fund modal inherited that as headroom. The fix is one optional field, `envelope.accountId` ("Backed by account" in the envelope dialog), read in two places: `envelopeCountsFor` decides whether the envelope's series joins `envelopeTotal` (household envelopes always; backed ones only when their account is selected), and `envelopeSpendingAccount` gains a rule 0 so the allowance drains from the backing account rather than the most-recent-expense guess, or from nothing at all when that account is not selected. Four things held on purpose: (a) **no backing account means household-wide, which is exactly the old behaviour** — so a file that never sets the field, and any forecast that selects every cash account, produces the same figures to the cent (audit-tested against the pre-change fixture). Spending history was considered as an automatic fallback and rejected: it flips with the latest expense, and an envelope whose last purchase came from an excluded account would silently drop out of a full forecast. (b) **The reserve envelope is always household-wide** — it is fed by sweeps from envelopes backed by any account, so no single account can claim it; `migrate` and the dialog both strip the field from it. (c) **A dangling id degrades to household** (`migrate` deletes it; `deleteAccount` strips it from the envelopes it backed and says so in the confirm) rather than excluding the envelope from every filtered forecast. (d) **The field is advisory, not enforced**: a Move-funds between envelopes backed by different accounts moves no cash between the accounts. The Help entry says so; a mismatch warning ("envelopes backed by X exceed X's balance") is the natural next step if it bites. Additive, no schema bump, same convention as `isReserve` and `pinned`. The Forecast tab lists what a selection left out under the summary table; the Fund modal needed no change because it re-forecasts (decision #27).

42. **Archive is hide, not close — and for an envelope it is also "no budget" (2026-09-08; closes roadmap #16).** Decision #1 refuses to delete anything with history, which left no way to retire a closed bank account or a finished envelope short of deleting its transactions. `archived: true` on either record takes it out of the lists, the pickers, the dashboard strip, Fund the month, close-out and the forecast's default account selection, and nothing else: an archived account still counts in balances and net worth (a closed account normally sits at zero, and if it doesn't the figure is real), an archived envelope keeps its balance earmarked (the confirm says to ↩ Return it first if that money should come back). The one accounting effect is deliberate and goes through a single chokepoint: `envMonthlyEquiv` returns 0 for an archived envelope, which is what removes it from the allowance projection, the monthly-budget totals, the close-out variance and the Reports budget column — no per-site guards. Three refusals: the reserve envelope (the flag is the sweep destination), and any record an *active* recurring still posts to (it would keep generating transactions into something the user called retired; deactivating the recurring is the honest step). Pickers use `pickerList`, which keeps an archived record only while the entry being edited names it, labelled "(archived)" — a re-saved old transaction must not silently lose its account, and a fresh one must not offer a retired one. Reports' budget-vs-actual shows an archived envelope only for months it had spending or funding, so history reads correctly without the row living on forever. Archiving scrubs the account from `forecastState.accountIds` and saved profiles exactly as delete does, and unpins. Both directions are one `pushUndo`. Additive, no schema bump; the flag is deleted rather than set false on unarchive so untouched files export unchanged.

43. **Envelope cards: a pace bar and a "⋯" menu replaced the tint fill and the six-button row (2026-09-08).** The card used to fill bodily with a hatched "security tint" whose height was balance ÷ budget (the CSS comment called it the signature element). It read as texture: the level was hard to see, the hatch competed with the figures, and it answered "how full is the envelope" when the mid-month question is "how is the month going". `envelopeCard` now renders `.ev-bar` — this month's spending against `envMonthlyEquiv`, with a tick at `dayOfMonth / daysInMonth` — and `data-pace` (`ok` / `ahead` / `over`) picks the colour in CSS; the old `data-state` survives only as a 3px left spine (red = negative balance, ochre = under a quarter of the budget). Reserve and unbudgeted envelopes get no bar. The actions row keeps Spend / Fund / Return and folds Edit / Archive / Delete into a `<details class="ev-more">` menu: native toggle, `summary` is already in `FOCUSABLE_SEL`, one document-level listener closes it on outside click or Escape, and each item closes its own menu before acting. Two CSS facts that are easy to lose: `.envelope` sets `overflow: visible` because `.card` is `overflow-x: auto` for its scroll-shadow trick and would clip the menu; and `.envelope:has(.ev-more[open])` lifts the card's `z-index` so the menu paints over the neighbouring cards. The `--tint-ink` tokens were deleted with the hatch. The README screenshots still show the old cards; regenerate them with the Playwright script when the next batch of visual changes lands.

44. **The forecast chart marks its low point, and the dashboard's low tile is toned by meaning (2026-09-08).** `drawForecast` picks a *featured* line — spendable whenever it is drawn, else the combined total — and gives it a native point at the minimum (`pointRadius` array, so hover and tooltip work), a shaded area when it is the sole line (`fill: 'origin'` with a two-hex-digit alpha appended to the theme token — `withAlpha` only appends when the token is six-digit hex, which every colour token is), and a hand-drawn label via the inline `forecastMarksPlugin`, which also draws a dashed zero line but **only when the y-range crosses zero** — a positive-only chart must not be stretched down to show it. Axis ticks format the ISO label through `Intl.DateTimeFormat` (`maxRotation: 0`; the year joins in only when the horizon spans two years) and the tooltip title goes through `fmtDate`. On the dashboard, `lowTone(value)` returns `'bad'` below zero, `'warn'` under `settings.forecastWarnBelow` (optional, set in Settings through `evalAmount`, deleted when cleared), else `''`; the tiles used to carry a red or amber border unconditionally, which made a healthy low look like an alarm. `lowToneNote` supplies the one-line reason. All chart colours still go through `themeColor()`.

45. **The phone header is one row plus a scrollbar-less tab strip (2026-09-09).** Below 720px the header used to take three rows (title, then Reload/Save wrapped, then tabs over a fat visible scrollbar). Now row 1 holds title + status + the three buttons (buttons at their small size, the status label truncating and hidden under 460px except in the `conflict` state, whose text must stay legible — the dot still carries the colour and the full text sits in the element's `title`), and the tab strip hides its scrollbar (`scrollbar-width: none` + the WebKit pseudo) while `data-fade` (`left` / `right` / `both` / `none`, maintained by `updateTabFades()` on scroll and resize) drives a `mask-image` edge fade so the cut-off tab reads as "more this way" rather than a bug. `render()` scrolls the active tab into view when the strip overflows, so a drill-through or `?view=` landing on an off-screen tab is visible. Nothing changes at 721px and up.

46. **One typeface, one icon set, a day-grouped transaction list (2026-09-09).** (a) The monospace "ledger" face is gone: `--font-mono` and its eight uses are replaced by the UI font with `font-variant-numeric: tabular-nums` (which is what actually aligns the decimals) and a touch more weight on the big figures; the eyebrow labels keep their tracking. (b) Controls no longer use emoji or text glyphs (📌 ⋮⋮ ↩ ⏭ ⚡ ⇄ ⤓ ⟳ 🌗 ⋯ ▾ ⎘ ×): `icon(name)` renders from an inline SVG sprite in `<body>` — 16px grid, `stroke: currentColor`, so the same icon is right in both themes and inherits a button's colour; the accounts pin fills when `aria-pressed="true"`. Help copy names the actions in words. (c) The Transactions table drops its date column for a `tr.tx-day` heading per day (`txRowsHTML`, shared by the first render and the filter pass), shows the type as a `.tx-type` dot with the word in a `.sr` span and the tooltip, and pins its `thead` under the app header — but **only at ≥900px**, because the sticky header needs the card to be `overflow: visible`, and below that width the table must keep the card's horizontal scroll. The app header's height is published as `--header-h` by `updateTabFades()` (it changes when the tab strip wraps), which is what the sticky `top` reads. Day rows carry no `data-tx`, so the 'c' duplicate shortcut and bulk selection ignore them.

47. **Budget vs actual carries bars and words, not signed variances (2026-09-09).** `budgetVsActualHTML` puts a `.bva-bar` under each Spent figure — the pace-bar rule from decision #43 (`ok` / `ahead` / `over`, the tick only when `ym` is the current month, since a past month is complete), tints `tr.bva-over`, and words the variance ("€50.00 over" red and bold, "€150.00 under" green, "on budget"); the old `+€50.00` in red asked the reader to remember that positive was bad. Budget-less rows (reserve, archived) get no bar and a dash. The figures are unchanged and still come from `envelopeMonthSummary`, so the table and close-out cannot disagree.

48. **Balances are cached for the duration of one render, and nowhere else (2026-09-09; closes roadmap #19).** `accountBalance` / `envelopeBalance` still scan every transaction — that simplicity is what the audit leans on — but a render used to pay for the same scan several times per id (cards, tiles, the dashboard forecast seeding every envelope, the pinned strip, the lowest-envelopes list). `render()` now calls `balanceCacheBegin()` after the no-data guard and `balanceCacheEnd()` in a `finally`, and the two helpers read through `_balCacheLive()`. The scope is deliberately the render pass and not "until the next mutation": mutation sites are many and a handler that reads, mutates and reads again before `saveDirty` would see a stale figure under a version-counter scheme, whereas nothing inside a render mutates transactions. Two cheap guards on top: the cache is keyed to the transactions array's identity **and** length, so `spendableMinAfterFunding`'s probe copy and any in-pass push bypass it (audit-tested). Modals and forecast reruns outside a render compute fresh, once, which is fine. If a profiler ever wants more, the next step is a version counter bumped in `saveDirty` / undo / redo / load — not a per-site cache.

49. **A hand-logged transaction can be linked to its due occurrence — offered in the review, never applied by itself (2026-09-09; closes roadmap #21).** Decision #21 left a plain "Add transaction" unaware of the recurring it fulfils, so the occurrence stayed due and the forecast folded it into idx 0 on top of the real row. `findHandLoggedMatch` proposes one candidate per due row: same type, same account (or the same from/to pair for a transfer), the amount equal to the cent, dated within `HAND_LOG_WINDOW_DAYS` (3) of the schedule, not itself `fromRecurringId`, not claimed by another row, closest date first. The envelope is deliberately not part of the key — a payment filed under a different envelope is still that payment. The due review shows the candidate under the row and defaults the action to **Link**; applying it stamps `tx.fromRecurringId = rec.id` (so it can't match twice and the forecast's coverage netting treats it like a generated row) and counts the row as resolved for the contiguous-prefix watermark rule of decision #12. The dashboard banner counts how many due rows have a candidate. It is an offer because the failure modes are asymmetric: an unlinked duplicate is a visible over-count the user can fix, a wrong automatic link silently hides a bill that is still due. Undo covers it with the rest of the review.

## Anti-patterns — don't do these

- **Don't refactor `pocket-envelopes.app` into modules.** Single-file is a feature.
- **Don't add CDN scripts** beyond the existing Chart.js (and Chart.js is on the vendor-locally list).
- **Don't hardcode hex colours in JS.** Route through `themeColor()` / `chartPalette()`. In CSS, text on a solid `--accent`/`--bad`/`--warn`/`--good` fill uses `var(--on-fill)`, never a literal ink colour.
- **Don't `parseFloat` user-typed amount fields.** Use `evalAmount()`.
- **Don't silently merge phone-captured transactions** into `data.transactions`. The review-and-accept banner is the contract.
- **Don't change `lastAppliedDate` semantics** without auditing `nextDue`, `dueRecurringOccurrences`, `applyDueRecurring`, and forecast — they're tightly coupled.
- **Don't add locale- or country-specific identifiers** (bank names, employer names, bonus schemes) to the app source — keep it generic; users populate their own data.
- **Don't capture undo inside `saveDirty()`.** Call `pushUndo(label)` explicitly at user-initiated destructive sites. Background saves (net-worth snapshot, file import, drag-reorder) must NOT clutter the undo stack — otherwise Ctrl-Z fires unexpectedly.
- **Don't invert mutations by hand to "undo" them.** Snapshot + restore is the contract. Inverse-op code would multiply bugs across every mutation site for no real-world memory win.
- **Don't read `tx.envelopeId` directly to compute an envelope's money** — a split tx has `envelopeId: null` and its amounts live in `splits[]`. Go through `txEnvelopePortion(tx, envId)` / `txEnvelopeDelta(tx, envId)` (both split-aware) so balances, reports, forecast and close-out agree. Reading `envelopeId` is fine for non-money purposes (suggestions, the spending-account heuristic), which degrade gracefully on splits.
- **Don't write directly to `envBudget_bak_*` keys.** Use `ensureDailyBackup()` / `restoreBackup()` / `deleteBackup()` so the `envBudget_bak_index` stays in sync. Out-of-band writes will silently break listing and pruning.
- **Don't book an `evalAmount()` result without an `isNaN` guard.** A cleared field or incomplete expression (e.g. `"14000+"`) returns `NaN`; an unguarded `data.transactions.push({ amount: NaN })` permanently poisons `accountBalance()` → net worth → forecast (every running sum becomes NaN, `fmt()` shows "—"). All four `evalAmount` save sites now guard — keep any new one consistent.
- **Don't call `bindReports()` without `renderReports()` having run first** in the same render — it reads the `_reportsAgg` cache that `renderReports` populates (falls back to a recompute, but that defeats the single-scan optimization).
- **Don't hand-add `for=` to modal field labels, or move controls out of their `.field` wrapper.** `openModal()` auto-links each `<label>` to the control inside its `.field`; keeping the structure intact is what gives every modal input an accessible name.
- **Don't rebuild recurring→tx field routing inline.** Call `recurringToTx(rec, date, amount)` — three sites used to duplicate the type dispatch and could silently drift.
- **Don't re-introduce a current-month "catch-up" into the allowance smoothing.** Charging the elapsed part of the month again double-counts spending that is already in the account balances (decision #34). If you touch the smoothing, re-run the invariant check: with allowances on vs off, the per-month delta must be exactly one month's allowance for every *full* future month, and the current month must equal budget minus what is already spent.
- **Don't collapse the forecast's per-envelope series back into one `envelopeTotal`, and don't drop the zero floor.** They are a single mechanism (decision #22). Without the floor, mirroring the allowance drain runs envelopes to −∞; without the mirror, every funded euro is deducted twice and "lowest spendable" punishes the user for funding. Any new projected envelope outflow must go through `envSeries[env.id]`, never straight onto the aggregate.
- **Don't predict the effect of a mutation on the forecast arithmetically.** Run the forecast with the mutation applied (`spendableMinAfterFunding` is the pattern: probe rows on a copy, restore in `finally`). Since decision #22 the spendable line is piecewise — clamped per envelope — so "X euros in makes the line X lower" is simply false, and the shortcut it replaced was off by up to the entire amount being tested (decision #27).
- **Don't link a hand-logged transaction to a recurring automatically, and don't loosen `findHandLoggedMatch`.** Exact amount, same account, three days: a looser rule (amount within 5%, any account) starts matching the wrong payment, and a match applied without the user choosing Link hides a bill that is still due (decision #49). And don't cache a balance across a mutation: the cache lives inside one `render()` pass on purpose (decision #48).
- **Don't offer a due occurrence the user skipped, and don't let `skippedDates` outlive the watermark.** Every reader of pending occurrences goes through `isSkippedOccurrence()`; the due review prunes skips at or before `lastAppliedDate` after advancing it, so the list only ever holds dates ahead of the watermark (decision #38). A new pending-occurrence reader that ignores it re-offers a bill the user said never happened.
- **Don't reset `txFilter` inside `render()`.** It is module-level on purpose so a filter survives the full re-render every save triggers; only the Clear button, drill-through and URL params replace it. `txSelected` IS cleared on render — a bulk selection must not silently outlive the mutation it was made for.
- **Don't render a tag by hand, and don't drop a tag you don't recognise.** Chips come from `tagChip()`, pickers from `tagOptions()`, and a tag that names nothing in `settings.tags` is data to preserve, not garbage to clean (decision #36). If you add a new place that builds a transaction object from scratch (the tx save handler, CSV import, `recurringToTx`), copy `tag` across explicitly — it is not in any spread.
- **Don't count an untagged transfer in the tag reports, and don't tag the return leg of a pass-through.** Tagged transfers are outflow-for-a-purpose by design; extending that to every transfer would report internal cash movement as spending (decision #36).
- **Don't put an emoji or a text glyph in a control, and don't add a monospace face for figures.** Icons come from `icon(name)` and the sprite (decision #46); a new icon is a new `<symbol>` on the same 16px stroke grid. Numbers align through `font-variant-numeric: tabular-nums`, not a second typeface.
- **Don't build an account or envelope `<option>` list from `data.accounts` / `data.envelopes` directly.** Go through `pickAccounts(selectedId)` / `pickEnvelopes(selectedId)` (or `activeAccounts()` / `activeEnvelopes()` for lists with no current selection) and append `archSuffix(x)` to the label — otherwise a retired account reappears in every new-transaction form, or an old transaction loses its account on re-save (decision #42). And don't add a per-site `!archived` guard to a budget total: `envMonthlyEquiv` already returns 0 for an archived envelope, and that single chokepoint is what keeps the totals, the allowance projection, close-out and Reports in agreement.
- **Don't read `env.accountId` as "the account this envelope spends from" anywhere except through `envelopeBackingAccount` / `envelopeCountsFor` / `envelopeSpendingAccount`.** It is optional, may dangle after a hand-edit, and is meaningless on the reserve envelope; the helpers encode all three (decision #41). And don't make a missing backing account mean anything other than household-wide — that default is what keeps every existing file's forecast identical.
- **Don't give a reserve envelope a budget, and don't add a second one.** A non-zero `budgetAmount` puts it back into the forecast's allowance drain and the monthly-budget totals — the zero is the mechanism, not cosmetics (decision #33). A second `isReserve` envelope makes the sweep destination ambiguous; `editEnvelope` enforces exactly one on save.
- **Don't implement a sweep as a one-sided expense/income.** `reset` un-earmarks money (back to spendable); `sweep` re-earmarks it (envelope → envelope). Using the `reset` accounting model for a sweep would return the leftover to spendable *and* credit the reserve, inventing money.
- **Don't count a one-sided envelope tx (`accountId: null`) as spending.** Guard with `isCashflowTx(tx)` — it's a "Return to spendable" / close-out reset / balance adjustment, not money leaving an account (decision #26). The mirror-image rule also holds: don't guard `funded` that way, since refills are legitimately account-less.
- **Don't assume `rec.months` is sorted, and don't remove the sort.** The `custom-months` generator's early `return` depends on chronological order; unsorted lists silently swallow occurrences (decision #25).
- **Don't reintroduce a localStorage mirror of `data` as a load-time fallback.** With multiple devices on one server file, preferring a per-browser copy resurrects records another device deleted. Dated backups (Settings → Backups) are the recovery path (decision #29).
- **Don't treat `writeFile()` as fire-and-forget.** It returns a boolean and can legitimately fail (server down, `409`). Callers that toast "Saved" must gate on the result, or the app will cheerfully claim it saved data that is only in RAM.
- **Don't auto-resolve a `409` by retrying without `If-Match`.** That is last-write-wins with extra steps and silently destroys the other device's edit. The conflict dialog is the contract (decision #30).
- **Don't build a data path from a bare filename in `serve.py`.** Go through `DATA_DIR` / `DATA_FILE` / `BAK_PREFIX`; a relative `open('finance-data.json')` would land in the program folder under the installer and silently fork the budget (decision #37).
- **Don't add a write path to `serve.py` that bypasses `_write_data()`.** The rotate → tmp → fsync → replace sequence and the `_data_lock` are what make saves atomic and race-free; a stray `open(DATA_FILE,'w')` reintroduces torn files.
- **Don't let the service worker cache `/data`, and don't make the shell cache-first.** Both undo the single-source-of-truth guarantee in different ways (decision #31). If you add an asset to `SHELL`, bump `CACHE_NAME` in the same edit.
- **Don't assume an unreachable server makes `fetch()` throw.** Behind a reverse proxy (`tailscale serve`) a stopped backend is a resolved 502. Any "did the network fail?" check needs the `!res.ok` branch too, in `sw.js` and in app code alike.
- **Don't widen the bind address by default.** `serve.py` now defaults to `127.0.0.1`, and `BIND=0.0.0.0` is the deliberate, per-run opt-in for multi-device use. When a reverse proxy such as `tailscale serve` fronts the app it connects over loopback anyway, so widening the bind re-exposes an unauthenticated app to the whole LAN for no gain.

## Git hygiene

Work lands between sessions (other machines, other agents), so never assume HEAD is where you left it. This was learned the hard way on 2026-05-27: a session amended v0.1.0 assuming HEAD was the initial-release commit, but HEAD had advanced through three new commits made between sessions (undo, backups, DST). The amend landed on the wrong commit and bundled the new fix into an unrelated commit message.

Rules of thumb before any git operation:

- **Always run `git log --oneline -8` first.** Verify HEAD matches what you expect from your own session memory. If it doesn't, *stop and ask*.
- **Before any destructive op** (`amend`, `reset --hard`, `tag -d`, `rebase`, force-push) inspect:
  1. `git log --oneline --decorate -8` — what commits exist, where tags point
  2. `git show <tag>` — confirm the tagged SHA matches your mental model
  3. `git status` — confirm working tree state matches your last edit
- **Never `git tag -d` and re-create a tag without verifying the old SHA in the deletion output line** (`Deleted tag 'vX.Y.Z' (was <sha>)`). If that SHA isn't what you expect, the tag has been moved by someone else; pause.
- **Never amend without `git log -1` confirming the message + SHA you're about to rewrite.** `--amend --no-edit` silently preserves the prior message even when the content is unrelated — exactly how the 2026-05-27 mishap happened.
- **Commit as yourself.** Never quote figures from a real budget in a commit message; a relative delta carries the same argument.
- **Recovery from a bad amend**: `git reset --soft HEAD@{1}` puts your changes back as staged uncommitted edits without losing anything. Combine with `git tag -d` + `git tag -a <sha>` to relocate tags. The orphan commits show up in `git fsck --unreachable` and get GC'd eventually.

## Smoke-test recipe

The Claude Preview MCP launch config at `.claude/launch.json` already points at `serve.py`. To smoke-test changes:
1. `preview_start` (name: `envelope-budget` — kept legacy launch.json name to avoid churn; the launch.json runs the project's `serve.py`)
2. App auto-loads at `/` (server rewrites to `/pocket-envelopes.app`)
3. `data` is a lexical `let`, NOT on `window`. Use `eval('data = …')` to seed test state from `preview_eval`. Stub `render` and `saveDirty` to no-ops if you want to skip the dashboard re-render path on seed data that's missing fields.
4. `preview_stop` when done. `serve.py` will auto-shut after 1800s idle anyway.

**Never smoke-test against the real `finance-data.json`** — the app now writes to the server automatically, so a test session mutates it for real. Copy `serve.py`, `pocket-envelopes.app` and `vendor/` into a scratch dir with a throwaway `finance-data.json`, and run it on a different port (`PORT=8799 IDLE_TIMEOUT=300 python serve.py`). To exercise the conflict path, edit the scratch file behind the app's back (any external write changes the ETag) and then trigger a save in the tab.

**Editing `pocket-envelopes.app` with Claude's tools:** the non-`.html` extension trips the Read/Edit binary-file guard (`This tool cannot read binary files`), even though the file is plain UTF-8 HTML. Workaround: `Copy-Item pocket-envelopes.app _edit.html`, Read/Edit the `.html` twin, then `Copy-Item _edit.html pocket-envelopes.app -Force` and delete the twin. `Grep` reads the `.app` directly (handy for locating lines). The copy is byte-exact, so encoding (incl. the 💰 emoji) is preserved.
